# Portable CI contract

Basis owns a reusable, locally validated pattern for low-cost GitHub Actions. It is a contract and a reference implementation, not repository infrastructure: Basis does not choose an organization's runners, labels, credentials, budgets, or per-repository check set. The pilot is [Alforge/ai #171](https://github.com/Alforge/ai/issues/171); do not roll the pattern out to the other organizations until the pilot is reviewed.

The expensive part of the current PR loop is not screenshot execution. It is repeated job startup, repeated checkout and dependency setup, repeated image provisioning, and running all of that for Draft commits that cannot merge. The recipe keeps the final gate at least as strict as today while spending no hosted runner minutes on routine Draft events.

## Event contract

| Event | Draft pull request | Ready pull request |
| --- | --- | --- |
| `opened` | 0 hosted jobs | full code suite plus `Required` |
| `synchronize` | 0 hosted jobs | full code suite plus `Required` |
| `reopened` | 0 hosted jobs | full code suite plus `Required` |
| `ready_for_review` | not applicable | full code suite plus `Required` for the current HEAD |
| `edited` (title or body) | 0 hosted jobs | title check only; `Required` reuses code results on the exact HEAD |
| `converted_to_draft` | 0 hosted jobs; the run exists only so concurrency cancels the in-flight Ready run | not applicable |
| push to the default branch | release path, independent of pull-request state | release path, independent of pull-request state |

The Draft state itself blocks merging, so a Draft must not post a green `Required` status. The recipe skips every job, including the required job, before runner allocation. A workflow run may still exist for a Draft event; that is free as long as every job is skipped.

A newer run in the same per-pull-request concurrency group cancels the older one. A cancelled or timed-out job is never success. Re-drafting cancels the in-flight Ready validation, and re-promotion revalidates the then-current HEAD rather than trusting an earlier promotion.

Use a separate `workflow_dispatch` workflow if a maintainer deliberately wants to debug a Draft. Keep it explicit and bounded; do not add an automatic Draft run or a "run everything but call it skipped" path.

## The required gate

Do not reduce `needs` with `contains(needs.*.result, 'failure')`. That expression passes `skipped`, `cancelled`, missing and `neutral` results, so it becomes a false green the moment a Draft is promoted.

The portable [required gate](../.github/actions/required-gate/README.md) fails closed and reuses prior results only in one narrow case:

```yaml
required:
  name: Required
  if: ${{ always() && !github.event.pull_request.draft }}
  needs: [quality, test, visual]
  runs-on: ${{ vars.CI_RUNNER || 'ubuntu-latest' }}
  permissions:
    checks: read
    contents: read
  steps:
    - uses: TroyAlford/basis/.github/actions/required-gate@<released-tag>
      with:
        github-token: ${{ github.token }}
        needs: ${{ toJSON(needs) }}
        head-sha: ${{ github.event.pull_request.head.sha }}
        check-names: |
          {"quality":"Quality","test":"Test","visual":"Visual"}
```

Every dependency must have succeeded in the current run. A dependency that was skipped may pass only by reusing a completed, non-skipped success on the exact head SHA, excluding the current run's own check runs. `failure`, `cancelled`, `timed_out`, a missing result, a `neutral` conclusion, a prior `skipped` result, or a check that never completes before the timeout fails the gate.

The gate reads check runs; it never writes statuses. Branch protection should require the calling job's name (`Required`), not each dependency. If a dependency has a `name:` that differs from its job id, pass `check-names`, and update branch protection if the `Required` job is renamed. Every mandatory check must be in `needs`; a check the gate does not receive is absent, not skipped.

## Security boundaries

Code checks run on `pull_request` with a read-only token unless the repository deliberately grants more. Do not run code checks on `pull_request_target`.

`pull_request_target` is for metadata workflows that need a write-scoped token, such as posting an informational title comment on a fork PR. Such a workflow must never check out or execute pull-request head code, must never pass secrets to it, and must never use the PR head SHA as a checkout ref. The reference title workflow only reads `github.event.pull_request.title` from the event payload and calls the GitHub API.

There is a branch-protection nuance: check runs from a `pull_request_target` workflow are associated with the base ref, not the pull-request head. If a title check must be a required status on the head SHA, run it on `pull_request` instead; the token is read-only on fork PRs, so comments are best-effort, but the job's exit status still enforces the title. Never resolve that by checking out PR code under the write-scoped `pull_request_target` token.

## Reference workflows

- [consumer-ci.yml](./examples/consumer-ci.yml) is the code workflow: one consolidated `quality` job (lint, typecheck, advisory Knip), a separate `test` job, a separate `visual` job, extension points for integration suites, and the single `Required` gate.
- [consumer-pr-title.yml](./examples/consumer-pr-title.yml) is the metadata workflow: `pull_request_target`, no checkout, gated on Ready.
- [events/](./examples/events) contains the Draft, Ready, title-edit and re-draft fixtures used by `act`.

Both examples select a runner with `${{ vars.CI_RUNNER || 'ubuntu-latest' }}`. The default is the existing GitHub-hosted runner; a repository that needs a larger hosted runner or a self-hosted label sets its own repository variable. No organization or OCI label is hardcoded in Basis.

The reusable release workflow now accepts a caller-provided `runs-on` input, defaulting to `ubuntu-latest`, and applies it to every release job with an explicit `ubuntu-latest` fallback for `push` and `workflow_dispatch`, where `inputs` is empty:

```yaml
jobs:
  release:
    permissions:
      contents: write
    uses: TroyAlford/basis/.github/workflows/release.yml@<released-tag>
    with:
      runs-on: ubuntu-latest
```

The value is a scheduling label, never interpolated into a shell command. Existing callers keep the default; the release triggers, permissions, outputs and release actions are unchanged. Basis's own jobs can keep whatever hosted runners they use.

## Local-first verification

Prerequisites: Bun, Docker with a running daemon, and optionally [`nektos/act`](https://github.com/nektos/act) for workflow parsing. The static tests need neither Docker nor network.

```bash
bun install
bun run ci:contract
bun run ci:verify
bun run lint
bun run lint:ts
bun test
bun run test:consumer
```

`bun run ci:contract` runs the static YAML event/job-graph contract tests and the reducer tests against a fake `gh`. It proves the event matrix, Draft gating, required-job graph, release runner input, and fail-closed reducer behaviour without a hosted runner.

`bun run ci:verify` runs those tests and, when `act` is installed, dry-runs the reference workflows, the reusable release workflow on `workflow_call`, and the release workflow on `push`. It never contacts GitHub Actions. Use `./` when invoking the hidden test directory directly: `bun test ./.github/ci`.

Validated locally with `act` 0.2.89: both reference workflows parse and dry-run against `docs/examples/events/ready-for-review.json`, and the release workflow dry-runs on both `workflow_call` and `push`. The two `act` invocations for the pull-request workflows are:

```bash
act pull_request --dryrun -P ubuntu-latest=catthehacker/ubuntu:act-latest \
  --local-repository "TroyAlford/basis@main=$PWD" --var CI_RUNNER=ubuntu-latest \
  --workflows docs/examples/consumer-ci.yml \
  --eventpath docs/examples/events/ready-for-review.json

act pull_request_target --dryrun -P ubuntu-latest=catthehacker/ubuntu:act-latest \
  --local-repository "TroyAlford/basis@main=$PWD" --var CI_RUNNER=ubuntu-latest \
  --workflows docs/examples/consumer-pr-title.yml \
  --eventpath docs/examples/events/ready-for-review.json
```

A consumer checkout omits `--local-repository` and resolves the pinned released action from its `uses:` tag. The `-P` mapping avoids `act`'s first-run image prompt; `--dryrun` does not pull it.

`act` is a workflow parser and local executor, not proof of hosted behaviour. It cannot reproduce GitHub-hosted image pull speeds or caches, billing-minute rounding, token permissions and fork behaviour, branch-protection check association, or every event semantic. Use it for the event matrix and job graph; use the static tests for the gate's negative cases; use one deliberately planned hosted confirmation after local proof. Do not push repeatedly to discover CI behaviour.

## Image provisioning benchmark

Measured on 2026-10-21 on the local sandbox: Linux 7.0.0-1009-oracle, aarch64, 4 vCPU, 24 GiB RAM, Docker 29.8.1, Bun 1.4.2, Playwright 1.63.0. The pinned image was `mcr.microsoft.com/playwright:v1.63.0-noble` at digest `sha256:eff16c30e6f3f4af0a03fa4b706120d5e9b0891c344a27d64559aff5900a4a27`, warm in the local cache (88 active containers were already using it).

Reproduce the warm measurements with `bun run bench:snapshot`; add `-- --save-load` to include the docker save/load artifact cost. The script never removes the image or running containers.

| Measurement | Result | Cache / command |
| --- | --- | --- |
| warm `docker pull` | 0.15–0.20 s | `docker pull mcr.microsoft.com/playwright:v1.63.0-noble`; manifest check, no layer download |
| warm container start | 0.33–0.49 s | `docker run --rm --pull missing <image> node -e 'console.log(process.version)'` |
| `docker save` | 16.6–23.9 s, 0.87 GiB tar | `docker save <image> -o <tempdir>/image.tar` |
| `docker load` | 9.0–9.7 s | `docker load -i <tempdir>/image.tar`; restore/load proxy, not a hosted cache action |
| one snapshot capture, warm image | 2.3–3.4 s over 4 runs | `bun test libraries/testing/matchScreenshot.test.tsx`; runtime starts one container |
| hosted cold image pull | 36–55 s per visual job | Alforge/ai pilot logs, GitHub-hosted amd64 runners |
| hosted setup | 17–21 s per job | Alforge/ai pilot logs |
| hosted 17–18 screenshot tests | 3–4 s | Alforge/ai pilot logs |

The local host is arm64 while GitHub-hosted runners are amd64, so a local cold pull would not be a like-for-like hosted measurement even if the shared Docker cache could be cleared. It could not: the pinned image had 88 active containers, and removing it would disrupt other work. The hosted pull and setup ranges above are reported pilot data, not numbers this change re-measured.

Decision: do not change `libraries/testing/browser.ts`. It already starts one pinned container and one browser per test run, reuses a page for element captures, and keeps application visits isolated. Screenshot execution is 3–4 s; cold provisioning is the cost. A consumer pre-pull only moves the pull into a named step and does not reduce billed minutes, because the job is billed either way. A local `docker save`/`load` cache would add a 0.87 GiB artifact and at least 9 s of restore time for a benefit that is not clearly cheaper than a hosted pull. A purpose-built image or any runtime change is not authorized without proof of identical rendered snapshots and a clear material saving. Prefer the workflow fix; keep an optional pre-pull only if it improves failure diagnostics.

## Before and after

The baseline is the current Alforge/ai pull-request loop described in #171: six independent code jobs (`lint`, `typecheck`, `test`, `knip`, `session-environment`, `visual`) plus a one-job `Required` on every Draft push, and a separate title job. The recipe consolidates lint, typecheck and advisory Knip into one `quality` job, keeps `test` and `visual` separate, and runs no code job on Draft events.

For a representative cycle of three Draft pushes followed by promotion:

| Cycle step | Current Alforge/ai | Recipe |
| --- | --- | --- |
| Draft pushes: code | 3 × 6 = 18 jobs | 0 jobs |
| Draft pushes: `Required` | 3 × 1 = 3 jobs | 0 jobs |
| Draft pushes: title | 3 × 1 = 3 jobs | 0 jobs |
| Promotion: code | 6 jobs | 3 jobs (`quality`, `test`, `visual`) |
| Promotion: `Required` | 1 job | 1 job |
| Promotion: title | 1 job | 1 job |
| **Total** | **32 jobs** | **5 jobs** |

That is 27 fewer hosted job allocations, or about 84% fewer, for the cycle. The setup saving is larger in wall-clock terms because the current loop repeats 17–21 s of setup for every code job on every Draft push. The visual image pull is paid four times in the current cycle (three Draft pushes plus promotion) and once in the recipe, so the reported 36–55 s pull is also reduced.

These are job-allocation arithmetic from reported data, not a new hosted measurement. GitHub rounds each billable job up to the nearest minute, so wall-clock seconds are not the billed quantity; job allocations and the per-job setup/pull share are the robust comparison. A job that spends 20 s on setup can still bill as one minute. The recipe does not collapse the unit and visual suites, does not drop the OpenCode/session-environment or integration checks from a consumer's set, and does not weaken branch protection. Those checks stay, but they run only after promotion.

No hosted confirmation was run for this change. Prove the candidate locally, then plan at most one hosted confirmation with the operator and record its actual job allocations before claiming production savings.

## Migration checklist

Use this for Alforge, TroyAlford-Projects, and NerdrageTools. Do the pilot first; do not mass-edit repositories.

- [ ] Map the repository's current jobs to `quality`, `test`, `visual`, and any isolated integration/session jobs. Keep suites that currently run in separate processes separate.
- [ ] Copy the reference workflows and replace the setup action, install command, and check commands with the repository's own. Do not copy Alforge-specific setup into Basis or another organization.
- [ ] Set `vars.CI_RUNNER` only if the repository needs a non-default runner; leave it unset to keep `ubuntu-latest`.
- [ ] Add the `Required` job to branch protection. Keep its name stable; remove individual job contexts if `Required` is now the single gate, or keep them as additional contexts.
- [ ] Keep the title workflow on `pull_request_target` only for metadata and comments, never checkout PR head code. If the title must be a required head-SHA check, use `pull_request` instead and accept best-effort comments on forks.
- [ ] Confirm the release workflow still triggers on the default branch and is not gated by Draft state. Pass `runs-on` only when the caller needs a different runner.
- [ ] Run `bun run ci:contract`, `bun run ci:verify`, `bun run lint`, `bun run lint:ts`, `bun test`, and `bun run test:consumer` locally. Record the results.
- [ ] Prove the event matrix with the fixtures: Draft open/push/reopen/edit/convert, Ready open/push/reopen/edit, and re-draft to re-promotion. Verify a missing, cancelled, skipped, neutral or stale result fails `Required`.
- [ ] Plan one hosted confirmation only after local proof and operator approval. Record job allocations, per-job durations, setup repetition, and image-pull share. Label hosted data separately from local estimates.
- [ ] Apply to Alforge/ai #171 first, review the pilot, then repeat for TroyAlford-Projects and NerdrageTools. Do not change Basis's shared runtime or release semantics as part of a consumer migration.

## Ownership boundary

Basis owns the portable contract, the reference workflows, the required-gate action, the local verification recipe, and the caller-selectable release runner input. Each consumer owns its event policy, check set, commands, runner labels, budgets, secrets, branch protection, and workflow files. Alforge/ai #171 owns its Draft-first PR lifecycle, explicit ready action, and its own workflow optimization and measurements.

Nothing here authorizes a privileged Docker socket on application runners, an OCI runner migration, a new CI service, a weakened visual suite, erased branch protections, or a privileged checkout of pull-request code. Those are separate decisions with separate security and cost cases.
