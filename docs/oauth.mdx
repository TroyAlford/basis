# OAuth

`basis/oauth` exports the shared cross-subdomain identity capability, `Identity`, and `basis/server` mounts a provider-agnostic OAuth flow on top of it.

```ts
import { Identity } from 'basis/oauth'

const identity = new Identity({
  provider: 'github',
  public: 'op://Vault/OAuth/client-id',
  secret: 'op://Vault/OAuth/client-secret',
  scope: Identity.Scope.Domain, // optional; defaults to Subdomain
})
```

`provider` names the cookie (`auth.github`, `auth.discord`), so host-only cookies from different providers cannot collide. `identity.set(request, headers, userId)` signs a user in; `set(..., null)` signs out. `identity.get(request)` returns the verified user id or `null`. The cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, and host-only by default, with a 30-day lifetime. `Identity.Scope.Domain` shares it with the parent domain where applicable.

## Server integration

`server.oauth` mounts `/api/oauth/login`, `/api/oauth/callback`, and `/api/oauth/logout`, owns the CSRF state cookie and redirects, and verifies the session capability. The login and callback requests are passed to `authorize` and `exchange`, so the redirect URI follows the host the flow started on. A `returnTo` query parameter on login or logout may be a relative path or an absolute URL on the same application (the current host, its parent domain, or a sibling subdomain); the flow stores it for the callback and rejects external targets.

```ts
const callbackFor = (request: Request): string =>
  `${new URL(request.url).origin}/api/oauth/callback`

const github = {
  authorize: (state: string, credentials: { public: string, secret: string }, request: Request) =>
    `https://github.com/login/oauth/authorize?client_id=${credentials.public}&redirect_uri=${encodeURIComponent(callbackFor(request))}&state=${state}`,
  exchange: async (code: string, credentials: { public: string, secret: string }, request: Request) => {
    const response = await fetch('https://github.com/login/oauth/access_token', {
      method: 'POST',
      headers: { accept: 'application/json', 'content-type': 'application/json' },
      body: JSON.stringify({
        client_id: credentials.public,
        client_secret: credentials.secret,
        code,
        redirect_uri: callbackFor(request),
      }),
    })
    const body = await response.json() as { access_token?: string }
    return body.access_token ?? null
  },
  userId: async (token: string) => {
    const response = await fetch('https://api.github.com/user', {
      headers: { authorization: `Bearer ${token}`, accept: 'application/vnd.github+json' },
    })
    if (!response.ok) return null
    const body = await response.json() as { email?: string, id?: number, name?: string }
    return body.id === undefined
      ? null
      : {
        displayName: body.name,
        email: body.email,
        subject: String(body.id),
      }
  },
}

server.oauth({
  session: identity,
  authorize: github.authorize,
  exchange: github.exchange,
  identity: token => github.userId(token),
})
```

`identity` may return a bare provider subject or an `OAuthIdentity` object with `subject`, `displayName`, and `email`. The profile is passed to canonical identity enrollment; omitted values remain absent, so required application fields fail closed instead of receiving synthesized values.

`OAuthOptions` also supports `logger`, `returnTo`, and `stateMaxAgeSeconds`. `returnTo` is the fallback destination when the request has no valid `returnTo` query value. Provider-specific endpoints, scopes, and error handling stay in the callback helpers; the flow itself remains provider-agnostic. Configuring OAuth or `server.identity(identity)` embeds the verified user id in the SPA runtime context.
