# ESLint

`basis/eslint` is the shared flat ESLint configuration. The internal `@basis/eslint-plugin` implements Basis-owned rules; consumers do not install or enumerate the plugin stack.

```js
// eslint.config.mjs
export { default } from 'basis/eslint'
```

Extend the policy with the provided factory instead of replacing it:

```js
import { createConfig } from 'basis/eslint'

export default createConfig({
  overrides: [
    { files: ['src/vendor/**'], rules: { 'no-console': 'off' } },
  ],
})
```

The policy includes repository style conventions such as import ordering, JSDoc requirements, object and interface ordering, and the no-paragraph-line-breaks documentation rule. It is a style policy: architecture and infrastructure opinions live in `basis compliance`, not in `basis/eslint`.

Database-facing policy:

- `@basis/transaction-sql-name` requires recognized database transaction callbacks to bind their SQL client as `sql`, with a safe rename autofix.
- `@basis/sql-template-format` formats recognized Bun SQL tagged templates with dprint's PostgreSQL plugin. It applies uppercase keywords, two-space indentation, top-level joins, blank lines between statements, and dprint's width-aware layout, including `CREATE TABLE`, `VALUES`, `ON CONFLICT`, comments, and PL/pgSQL bodies. The formatter only applies layout fixes; it does not validate SQL or report style policy. Quoted text and JavaScript interpolations are preserved byte-for-byte.
- `@basis/sql-template-valid` parses recognized SQL templates with `libpg-query` and reports malformed PostgreSQL. It is a warning-only lint diagnostic and does not apply a fix.
- `@basis/sql-identifier-style` warns about unquoted identifiers that are not snake_case, such as `userId`, `DisplayName`, or `UserGroup`. Quoted identifiers are accepted because the author chose their spelling. It does not apply a fix.
- `@basis/entity-definition-format` applies to `**/*.entities.json`, enforcing canonical entity key order and the exact canonical field vocabulary. The same validator checks entity JSON examples in the documentation tree.

`basis lint` applies the style policy, reports warning-only SQL diagnostics as actionable findings, and runs the typechecker; `basis format` applies the autofixes and ignores warning-only diagnostics. `basis compliance` runs the same style/typecheck surface plus the architecture and infrastructure rules, and always uses the Basis-owned compliance configuration.
