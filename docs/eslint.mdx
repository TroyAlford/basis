# ESLint

`basis/eslint` is the shared flat ESLint configuration. The internal `@basis/eslint-plugin` implements Basis-owned rules; consumers do not install or enumerate the plugin stack.

```js
// eslint.config.mjs
export { default } from 'basis/eslint'
```

Extend the policy with the provided factory instead of replacing it:

```js
import { createConfig } from 'basis/eslint'

export default createConfig({
  overrides: [
    { files: ['src/vendor/**'], rules: { 'no-console': 'off' } },
  ],
})
```

The policy includes repository style conventions such as import ordering, JSDoc requirements, object and interface ordering, and the no-paragraph-line-breaks documentation rule. It is a style policy: architecture and infrastructure opinions live in `basis compliance`, not in `basis/eslint`.

Database-facing policy:

- `@basis/transaction-sql-name` requires recognized database transaction callbacks to bind their SQL client as `sql`, with a safe rename autofix.
- `@basis/sql-template-format` formats recognized Bun SQL tagged templates through the PostgreSQL syntax tree (`libpg-query`, MIT): a recursive AST printer composes a `SqlDoc` document, one renderer applies structure and indentation, and semantic verification compares the parsed result before an autofix is offered. The canonical layout uses uppercase keywords, one clause per line, structural line breaks for `SELECT`/`FROM`/`WHERE`/`GROUP BY`/`ORDER BY`/`RETURNING`, `AND`/`OR` attached to their condition, one `VALUES` row per line, one column or constraint per line in `CREATE TABLE`, indented CTE and subquery bodies, and stable two-space indentation. Identifiers in identifier positions are quoted canonically while preserving their source spelling; SQL keywords, literals, parameters, operators, and built-in types remain unquoted, built-in functions use canonical uppercase names, and user-defined functions stay lowercase and unquoted. Every template interpolation is preserved; placeholders are collision-safe and an interpolation that cannot be represented safely produces no autofix. PL/pgSQL bodies are parsed and formatted with the same document model, including declarations, control flow, assignments, dynamic SQL, and exceptions. Unsupported PostgreSQL nodes and PL/pgSQL statements produce an explicit non-fixable diagnostic naming the construct; malformed SQL and internal verification failures also produce no autofix. A single statement omits its trailing semicolon, multiple statements keep semicolons with a blank line between them, and comments stay with their structural block.
- `@basis/entity-definition-format` applies to `**/*.entities.json`, enforcing canonical entity key order and the exact canonical field vocabulary. The same validator checks entity JSON examples in the documentation tree.

`basis lint` applies the style policy and runs the typechecker; `basis format` applies the autofixes. `basis compliance` runs the same style/typecheck surface plus the architecture and infrastructure rules, and always uses the Basis-owned compliance configuration.
