# Server

`basis/server` provides the Bun application server used by Basis apps. One `Server` always runs live from source through Bun HMR and renders the application on the server before hydrating it in the browser.

```ts
import { Server } from 'basis/server'

const server = new Server()
  .root(import.meta.dir)
  .context(async request => loadApplicationContext(request))
  .main('./Application.tsx')
  .start({
    hostname: Bun.env.HOST ?? '127.0.0.1',
    port: Number(Bun.env.PORT ?? 80),
    version: Bun.env.VERSION ?? 'development',
  })
```

`root` resolves relative entrypoints and assets, `context` loads request-scoped application data, `main` registers the application component, and `assets` serves a static directory. `start` binds the HTTP server; `stop` keeps its synchronous contract, while `shutdown()` waits for owned capabilities such as the database pool. `main` modules must export `Application` or a default React component; Basis renders it on the server, injects the request context as bootstrap data, and hydrates it in the browser.

## Lifecycle

Bun's dev server owns the module graph, file watching, HMR, and React Fast Refresh. Basis watches application source for the server-rendered component and rebuilds the live SSR module after a change, so a subsequent request sees the updated `main` component or imported dependency without restarting the server. Versioned SSR artifacts are coalesced and cleaned after supersession; shutdown removes the server-owned artifact scope. The same source path handles `SIGINT`/`SIGTERM` through graceful shutdown.

`/api/health` is the readiness API. It stays `503 starting` until the browser shell, the configured SSR application module, and any configured database pool are ready, reports `503 error` on failure, and returns `200` only when the application is ready. `server.ready()` exposes the same promise.

## API routes

```ts
import { HttpVerb, Server } from 'basis/server'

new Server()
  .api([HttpVerb.Get], 'hello/:name', ({ name }, { logger }) => {
    logger.info(`hello ${name}`)
    return new Response(`Hello, ${name}`)
  })
```

API templates are served under `/api`; root paths remain the SPA surface. Handlers receive the matched params, the request, the server logger, and the typed application context under `context.context`.

## Request context

`context(loader)` defines the application data a request carries. The loader runs once per request; its result is passed to API handlers and to the automatically server-rendered `main` component.

```ts
type AppContext = {
  campaign: Campaign
  preferences: Preferences
  user: User | null
}

new Server<AppContext>()
  .context(async request => loadApplicationContext(request))
  .main('./Application.tsx')
  .api([HttpVerb.Get], 'campaign', (_params, { context }) => {
    return Response.json(context.campaign)
  })
```

The loader receives the request and should return a JSON-serializable value. Basis resolves the verified identity first, then runs the loader and the SSR render inside the same actor scope used by API handlers, so RLS applies consistently. Keep server-only capabilities such as `db`, `identity`, and the logger on the standard `RouteContext`; the application context is the shape embedded into the SSR bootstrap and hydrated in the browser.

## Static files

`assets(folder)` serves a fixed asset directory. `mount(prefix, folder, { allow })` serves an allow-listed directory under a URL prefix. Both reject missing files, traversal, and Basis-owned `.basis` state, including symlink aliases, so internal credentials cannot be served as static content.

## Live transports

`sse(route, handler)` registers a GET event stream and owns framing, disconnect cleanup, and a bounded buffer. `socket(route, handlers)` registers a WebSocket route with the same `open`/`message`/`close` lifecycle used by the server's own HMR transport.

```ts
server.mount('/vendor', './vendor', { allow: ['chart.js'] })

server.sse('events', (params, { logger }, channel) => {
  const timer = setInterval(() => channel.send('snapshot', currentState()), 2_000)
  channel.onClose(() => clearInterval(timer))
})

server.socket('room/:id', {
  open: socket => socket.publish('joined', { id: socket.params.id }),
  message: (socket, data) => socket.publish('echo', String(data)),
})
```

`mount` rejects traversal and Basis-owned `.basis` state, including symlink targets. SSE buffers are bounded, so a client that stops reading drops frames rather than growing memory without limit.

## Logging and runtime context

`Server` owns a standard Basis logger and writes lifecycle output through it. Read it with `server.logger`, or inject a custom logger through `start({ logger })`. Runtime facts (`SERVICE_NAME`, `VERSION`, `GIT_SHA`) are embedded into the SPA shell; `server.runtime` exposes the same facts to the host.

## Page titles

`basis/react` exports `Head` and `HeadProvider`. During SSR, `Head` collects the title synchronously for the shell. In the browser, title updates happen after commit, not during React's render phase. Server output escapes the title exactly once.

## Favicon and icons

Every server serves `/assets/favicon`. Configure a file, `Bun.file`, or an icon class with `server.favicon(input, options)`. Without configuration it discovers `favicon.*` in the working directory, app root, and assets folder, eventually falling back to the Basis mark. `server.icons({ Name: IconClass })` registers standalone SVGs at `/icons/{Name}.svg`.

## Embedding

`server.handle(request)` dispatches one request through the same routes used by a bound server, for hosts that mount Basis inside another fetch handler. SSE responses opt out of the HTTP idle timeout automatically.

## Database and authorization

`server.graph(graph)` composes the canonical graph and installs compiled PostgreSQL row-level security. See [Authorization & Row-Level Security](./authorization.mdx) for bootstrap, grants, request actor binding, and the restricted-role boundary.

`Graph.physicalSchema` plus `DDL.introspect`/`DDL.plan` provide the canonical read-only schema inspection and planning surface. See [Schema Inspection & Planning](./schema.mdx).

`server.database()` configures the zero-config managed PostgreSQL capability. See [Database & Transactions](./database.mdx) for pool lifecycle, `db.sql`, transactions, health, and managed storage, and [Query Language](./query-language.mdx) for the canonical predicate and grammar contract.
