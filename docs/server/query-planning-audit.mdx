## Identity contract conflict

The public reference hydration object is always:

```ts
{ entity: string, id: string, name: string }
```

Therefore an apparently ID-only path such as `workspace.id` still includes the inherited `name` in its reference object. For a final concrete target:

- `id` is selected from the concrete alias;
- `entity` is the compiler-known concrete type;
- `name` is selected from `Entity`, so the inherited-storage join is required.

Example generated SQL for `Document { fields: ["id", "workspace.id"] }`:

```sql
SELECT t."id" AS "id",
       'Workspace' AS "workspace__entity",
       b1."id" AS "workspace__id",
       r2."name" AS "workspace__name"
FROM "Document" "t"
LEFT JOIN (
  "Workspace" "b1"
  INNER JOIN "Entity" "r2" ON "r2"."id" = "b1"."id"
) ON "b1"."id" = t."workspace.id"
```

There is one physical `Entity` occurrence. Its required consumer is the inherited `name`; the ID and static type do not consume it.

For an abstract `Card` target:

```sql
r2."entity" AS "card__entity",
b1."id" AS "card__id",
r2."name" AS "card__name"
```

The root is consumed for the runtime discriminator and inherited name.

For a genuinely universal `Entity` target, the root is the only relation and supplies all three identity properties.

## What Stage 3 eliminated

The collection compiler now builds a count-only adapter for `$matched` and `$total`. Those scopes project identity only instead of rebuilding the complete nested target projection. Relationship-owned fields are projected from the relationship edge rather than by joining the target/root relation again.

Example count-only matched scope:

```sql
SELECT count(*)::int
FROM (
  SELECT cm5."id" AS "id"
  FROM "Printing" "cm5"
  WHERE EXISTS (
    SELECT 1
    FROM "DeckPrinting" "cj3"
    JOIN "Printing" "ct1" ON "ct1"."id" = "cj3"."printing.id"
    JOIN "Entity" "cr2" ON "cr2"."id" = "ct1"."id"
    WHERE "cj3"."deck.id" = "t"."id"
      AND (ct1."title" IS NOT DISTINCT FROM $2)
      AND ct1."id" = "cm5"."id"
  )
) AS "__member"
```

The count scope contains no Card, Face, Panel, or Art projection.

Relationship quantity now reads only the edge:

```sql
SELECT json_build_object('quantity', "cj3"."quantity")
FROM "DeckPrinting" "cj3"
WHERE "cj3"."deck.id" = "t"."id"
  AND "cj3"."printing.id" = "__child"."id"
```

Stage 3 reduced the saved MTG SQL from 24,659 bytes / 73 `Entity` joins to 11,817 bytes / 28 `Entity` joins. The remaining 28 joins are identity occurrences in the item and minimal count/existence scopes; this is not an authorization fix.

## Deferred

The universal `Entity` SELECT policy and its per-query expansion are unchanged. Stage 4 will establish the current PostgreSQL permission/RLS contract and compare the root storage access alternatives. No Graph policy or collection-planning change is part of this correction.
