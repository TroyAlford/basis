# Authorization & Row-Level Security

Basis owns one canonical application graph. The graph declares the ontology, the stable roles that exist, and the role/action/row permissions that PostgreSQL enforces. Loading a graph never mutates the database. `server.graph(graph)` puts `server.db` on the restricted application role, and PostgreSQL compiles the graph's permissions into real row-level-security policies.

```ts
import { Action, Graph, Server } from 'basis/server'

enum Capability {
  ManageArticle = 'manageArticle',
  ViewArticle = 'viewArticle',
}

const graph = new Graph({
  entities: [{
    name: 'Article',
    fields: [
      { field: 'title', type: 'String' },
      { field: 'owner', type: 'Entity', target: 'User' },
    ],
    security: {
      [Action.Read]: [{
        grant: Capability.ViewArticle,
        where: { field: 'owner', operator: '$eq', value: '$me' },
      }],
      [Action.Create]: { grant: Capability.ManageArticle },
      [Action.Update]: { grant: Capability.ManageArticle },
      [Action.Delete]: { grant: Capability.ManageArticle },
    },
  }],
  grants: {
    [Capability.ManageArticle]: { description: 'Manage articles' },
    [Capability.ViewArticle]: { description: 'View articles' },
  },
  roles: {
    editor: { name: 'Editor', grants: [Capability.ViewArticle] },
    administrator: {
      name: 'Administrator',
      grants: [Capability.ManageArticle, Capability.ViewArticle],
    },
  },
})

const server = new Server()
  .root(import.meta.dir)
  .graph(graph)
  .database()
  .start()
```
The application root conventionally exports `graph.ts` as `export default new Graph({...})`. Keep the application graph in one module and pass it to the server. `Graph` composes the application ontology with the system `User`, `Role`, `ExternalIdentity`, and `UserRole` definitions. Application `User` inherits `Entity`'s `id`, `name`, and `entity`; do not redeclare those fields. `Role` is an identified entity with a stable UUID `id`, an inherited mutable `name`, and an optional `description`.

## Roles and membership

The graph defines which roles exist. Public is the built-in principal that applies to anonymous and signed-in requests. Administrator is the built-in administration role. Additional roles use stable UUID keys or ordinary role declarations:

```ts
const roles = new Map([
  ['00000000-0000-4000-8000-000000000010', { name: 'Reviewer' }],
])
```

`UserRole` memberships are live records managed through `server.auth`; they are not graph declarations or seed memberships:

```ts
await server.auth!.bootstrap({
  provider: 'github',
  subject: 'operator-subject',
  email: 'operator@example.com',
})

await server.auth!.assignRole(userId, 'editor')
await server.auth!.removeRole(userId, 'editor')
```

Install the graph schema first through reviewed `DDL.plan → review → apply`; `bootstrap()` does not create or reconcile schema objects. It invokes the same canonical `basis.enroll_identity` function used by OAuth and adds the initial administrator membership. It is an explicit trusted operator action: never call it from an ordinary request handler, and never grant administration on first OAuth login automatically.

Automatic creation of a new `User` requires exactly one concrete `User` descendant. A graph may declare multiple concrete User subtypes for application-managed accounts; existing provider bindings still resolve, but a new automatic signup raises an explicit ambiguity error instead of choosing by declaration order. Enrollment supplies the canonical root name and the optional `User.email` value only; OAuth receives those profile values from the provider `identity` callback. It does not synthesize application-owned fields. If the selected User or one of its concrete subtypes has a required field that the enrollment call does not provide, PostgreSQL rejects creation and leaves no partial identity behind.

## Capabilities, roles, and security

The graph declares reusable **capabilities** in `grants`; a capability is a named positive permission, not a role attachment:

```ts
grants: {
  [Capability.ViewCampaigns]: { description: 'View campaigns' },
  [Capability.ManageCampaigns]: { description: 'Manage campaigns' },
}
```

Roles group capabilities. A user receives capabilities through verified `UserRole` membership in those roles; multiple roles may confer the same capability:

```ts
roles: {
  advisor: { name: 'Advisor', grants: [Capability.ViewCampaigns] },
  administrator: {
    name: 'Administrator',
    grants: [Capability.ViewCampaigns, Capability.ManageCampaigns],
  },
}
```

Each entity and named relationship owns an action-keyed `security` declaration. An action value is either explicit `Security.Public` or one or more alternative rules combined with OR. Each rule requires one of `grant` or `role`, optionally combined with a canonical row predicate in `where`:

```ts
security: {
  [Action.Read]: [
    { grant: Capability.ManageCampaigns },
    {
      grant: Capability.ViewCampaigns,
      where: { field: 'owner', operator: '$eq', value: '$me' },
    },
  ],
  [Action.Update]: { grant: Capability.ManageCampaigns },
  [Action.Delete]: { grant: Capability.ManageCampaigns },
  // Create omitted means denied.
}
```

- Missing action means denied, for reads and writes.
- Public access is explicit only: `[Action.Read]: Security.Public`; it never implies another action.
- A `{ role: 'someRole' }` rule requires that Graph role; `{ grant: Capability.X }` requires any role that confers the capability.
- Rules are positive alternatives. No negative grant or precedence exists.
- Every `create`, `update`, and `delete` additionally requires `read` for the same row. A create must satisfy read on the proposed resulting row; it cannot be created only to become visible after a later membership insert.
- One security declaration owns an entity hierarchy. If an entity declares `security`, none of its ancestors or descendants may declare one, even for disjoint actions; Graph construction fails with both owner names. A single declaration inherits unchanged to all physical descendants. Siblings may each declare security when no ancestor does.

The closed action vocabulary is `read`, `create`, `update`, `delete`, and `manage`. `manage` is an administration qualifier and cannot carry a row predicate. Predicates use the same `Filter`/`Predicate`/`QueryNormalizer` vocabulary as entity queries. Graph changes require a new graph and schema plan; there is no runtime grant registry duplicating the graph.

Graph predicates are normalized when the graph loads and compiled into PostgreSQL `CREATE POLICY ... USING (...)` and `WITH CHECK (...)` expressions. RLS covers the universal `Entity` root, every MTI ancestor and concrete table, and every named relationship table. Reads deny by returning no rows. Default deny applies to tables without a matching action declaration.

The previous target-bound `grants: [{ role, action, target, predicate }]` form is accepted only as a compatibility adapter and normalizes into the same canonical grant list; new graphs should use capabilities and entity/relationship security.

## Relationship membership predicates

Graph roles are global role memberships. A resource-specific membership is ordinary Graph relationship data, not another global role. Declare the relationship and grant access through its collection navigation:

```ts
enum WorkspaceCapability {
  View = 'viewWorkspace',
  Edit = 'editWorkspace',
}

enum MembershipRole {
  Owner = 'Owner',
  Viewer = 'Viewer',
}

const graph = new Graph({
  entities: [
    {
      name: 'Workspace',
      fields: [],
      security: {
        [Action.Read]: {
          grant: WorkspaceCapability.View,
          where: 'members $contains (id = $me)',
        },
        [Action.Update]: {
          grant: WorkspaceCapability.Edit,
          where: {
            field: 'members',
            operator: '$contains',
            filters: [{
              operator: '$and',
              filters: [
                { field: 'id', operator: '$eq', value: '$me' },
                {
                  field: 'workspaceMembership.role',
                  operator: '$eq',
                  value: MembershipRole.Owner,
                },
              ],
            }],
          },
        },
      },
    },
    { name: 'User', fields: [] },
  ],
  relationships: [{
    name: 'WorkspaceMembership',
    between: [
      { field: 'workspace', target: 'Workspace', inverse: 'members' },
      { field: 'user', target: 'User', inverse: 'workspaces' },
    ],
    fields: [{ field: 'role', type: 'String' }],
  }],
  grants: {
    [WorkspaceCapability.View]: { description: 'View a workspace' },
    [WorkspaceCapability.Edit]: { description: 'Edit a workspace' },
  },
  roles: {
    member: { grants: [WorkspaceCapability.View], name: 'Workspace member' },
    owner: {
      name: 'Workspace owner',
      grants: [WorkspaceCapability.View, WorkspaceCapability.Edit],
    },
  },
})
```
`members` is the inverse collection declared by the authenticated endpoint. `$me` is the verified transaction actor, so this predicate means: the current actor is connected to the Workspace by at least one `WorkspaceMembership`. An anonymous actor has no actor id and does not match. Changing membership rows changes access immediately; no graph rebuild or policy reinstall is required.

Relationship-owned scalar properties participate through the lower-cased relationship-name prefix. Keep the identity and role requirements in one member requirement so PostgreSQL evaluates them against the same relationship row:

```ts
[Action.Update]: {
  grant: WorkspaceCapability.Edit,
  where: {
    field: 'members',
    operator: '$contains',
    filters: [{
      operator: '$and',
      filters: [
        { field: 'id', operator: '$eq', value: '$me' },
        {
          field: 'workspaceMembership.role',
          operator: '$eq',
          value: MembershipRole.Owner,
        },
      ],
    }],
  },
}
```

The equivalent structured predicate is:

```ts
{
  field: 'members',
  operator: '$contains',
  filters: [{
    operator: '$and',
    filters: [
      { field: 'id', operator: '$eq', value: '$me' },
      { field: 'workspaceMembership.role', operator: '$eq', value: MembershipRole.Owner },
    ],
  }],
}
```

Authorization predicates support existential `$contains` with exactly one member requirement, `$empty`, logical `$and`/`$or`/`$not`, and ordinary comparisons on the matched identity and relationship-owned scalar fields. Inverse collections and named-relationship collections both work. Multiple independent `$contains` requirements for the same collection, nested collections, `$all`, arrays/JSON relationship properties, inherited non-root collection target fields, and cross-collection captures are rejected because their authorization meaning is ambiguous or not bounded.

Collection predicates are compiled through a generated, row-scoped Boolean policy helper. The helper uses `SECURITY DEFINER` with a fixed search path and is executable only by the application role; its body contains the validated Graph predicate and returns only a Boolean. It reads the transaction-local `actor.id`, so it cannot expose membership rows, grant table visibility, or create a privileged application capability. The membership and resource tables keep their own RLS policies, including when `FORCE ROW LEVEL SECURITY` is enabled.

A resource role such as Owner, Editor, or Viewer is relationship data, not a Graph role. Applications may still enforce domain rules such as preventing removal of the last Owner in ordinary application transactions. Existing direct predicates such as `owner = $me` continue to use the unchanged policy path.

## `$me` is search shorthand

`$me` is available in ordinary entity searches, separate from RLS:

```ts
const mine = await context.db!.query('Article', {
  fields: ['id', 'title'],
  where: 'owner = $me',
})
```

Both `owner == $me` and `{ field: 'owner', operator: '$eq', value: '$me' }` compare the stored `owner.id` with the current transaction's `actor.id`. Literal ids, `null`, and `!=` remain ordinary identity comparisons. A filter can voluntarily restrict a user even when RLS allows every row; filters never grant access. Direct SQL remains subject to RLS independently of any application search.

## Request transactions

The server resolves the verified canonical actor once at API dispatch. `RouteContext.identity` is that canonical id (or `null`), and `RouteContext.db` is the request-scoped database capability.

```ts
server.api([HttpVerb.Get], 'articles', async (_params, context) => {
  return Response.json(await context.db!.query('Article', {
    fields: ['id', 'title'],
  }))
})
```

Every ordinary application transaction runs through the native Bun `db.tx` path. Before caller SQL, `db.tx` sets the transaction-local `actor.id` setting with `set_config('actor.id', ..., true)`, including an explicit empty value for anonymous or non-request work. `db.query` uses the same transaction path. Nested savepoints, rollback, concurrent requests, and pooled connection reuse cannot carry the setting beyond the transaction.

`actor.id` is a context setting, not a cryptographically unforgeable principal. The accepted trust boundary is the application transaction/SQL-emission layer: it must use parameterized SQL and must not expose arbitrary untrusted SQL execution. RLS protects ordinary application queries and mistakes in filtering; it does not claim to defend against malicious application-role SQL deliberately overwriting `actor.id`.

## PostgreSQL privilege boundary

With a graph configured, `server.db`, `RouteContext.db`, and request-scoped queries always use the restricted application role (`basis_app` by default). Managed PostgreSQL provisions that role through the owner connection, stores its random password under `.basis/database/`, and closes the privileged provisioning connection afterwards. The owner credential is never exposed through `server.db` or `RouteContext`.

The administrative connection is an internal provisioning capability and is not available to ordinary handlers. The application role must be `NOSUPERUSER`, `NOBYPASSRLS`, and not the table owner. Bootstrap and schema DDL remain trusted administrative operations. RLS is enabled on the root, MTI/relationships, and security metadata; `FORCE ROW LEVEL SECURITY` is applied when provisioning runs with owner privilege.

## Inspection and administration

`server.auth!.can(action, target, row?)` executes the compiled policy expression and returns whether PostgreSQL permits the action for the current request actor. `server.auth!.effective(userId)` lists the expanded capability/role grants effective for a user, including explicit Public grants. `server.auth!.revokeIdentity(provider, subject)` revokes a provider binding.

Identity resolution and enrollment use one narrow system-owned security-definer function. OAuth calls it through the restricted application path; `bootstrap()` invokes the same function through its administrative connection. Request-time enrollment does not require the owner credential. Provider subjects are never treated as canonical entity ids, and revoked bindings fail closed. The administrative connection remains reserved for explicit bootstrap and schema provisioning.

The graph's roles, capabilities, entity/relationship security declarations, RLS policies, schemas, indexes, and security functions are part of the typed physical schema compiled by `Graph.physicalSchema` and planned by `DDL.plan`. See [Schema Inspection & Planning](./schema.mdx).
