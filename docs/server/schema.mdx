# Schema Inspection & Planning

The canonical Graph-owned ontology has one typed physical representation. Fresh installs, desired snapshots, and live catalog introspection all use the same table, column, index, constraint, function, trigger, policy, extension, and authorization objects.

## Desired physical schema

```ts
const model = new Graph({ entities, relationships, roles, grants })
const desired = model.physicalSchema('basis_app', false)
```

`PhysicalSchema` contains typed tables and columns, primary keys and defaults, indexes, foreign-key constraints, lifecycle functions and triggers, graph security functions, RLS policies, graph-managed role rows, role/table/schema/function grants, RLS flags, schemas, and extensions. `Graph.physicalSchema` compiles the ontology and adds the graph's roles and compiled policies. It feeds the one plan, review, and apply path.

## Read-only introspection

```ts
const actual = await DDL.introspect(ownerSql) // trusted catalog connection
```

`DDL.introspect` reads `information_schema`, `pg_catalog`, `pg_indexes`, `pg_proc`, `pg_trigger`, and `pg_policies`. It never creates, alters, or drops an object.

## Planning

```ts
const plan = DDL.plan({
  actual,
  desired: nextGraph,
  previous: deployedGraph,
  previousPhysical: deployedPhysical,
  appRole: 'basis_app',
  superuser: true,
})
```

Supply the historical compiled artifact with `previousPhysical` when planning an existing deployment. Production Graph-backed servers require the approved artifact for the exact configured Graph through `server.migration(artifact)` and perform only `DDL.readiness` on startup. An upgrade without that artifact fails closed rather than recompiling previous intent with the current generator. The planner uses that approved artifact instead of recompiling previous intent with the current generator. A change in generated policy SQL is therefore migration-worthy even when the old and new SQL are semantically equivalent. PostgreSQL's catalog deparsing is normalized only at the previous→actual drift boundary.

`DDL.plan` is deterministic and read-only. Each operation carries a stable id, target, intended SQL, dependency edges, preconditions, and risk classification. Unresolved dependency cycles fail closed instead of executing an arbitrary pending operation. A populated-table add-column operation is marked `data`; security changes are marked `review`. New tables carry their RLS, grant, index, and constraint dependencies. Intentional previous→desired changes become operations, including policy replacement and graph role metadata updates; unexplained differences from the compiled previous physical state are drift.

The plan reports:

- `drift` when the live catalog contains an unexpected table, column, index, constraint, function, trigger, or policy.
- `ambiguities` when a previous table disappears and a new desired table appears. The planner never guesses a rename.
- `blocked` when drift or ambiguity requires an explicit reviewed decision.

Applying a plan is never automatic. `DDL.review` creates the immutable artifact and `DDL.apply` is the only execution path; `DDL.hash(source)` produces the deterministic SHA-256 source hash used by snapshots.

## Reviewed migration artifacts

A plan is read-only input to the migration review boundary. `DDL.review` turns it into a deterministic, checksummed artifact. Data-changing operations and unresolved renames require explicit approved SQL; a blocked plan with live drift cannot be reviewed.

```ts
const artifact = DDL.review(plan, {
  schema: 'public',
  version: '2026-11-08-001',
  resolutions: [{
    operationId: 'alter-column:Note:amount',
    approved: true,
    sql: 'ALTER TABLE "Note" ALTER COLUMN "amount" TYPE double precision USING "amount"::double precision',
  }],
})

const result = await DDL.apply(adminSql, artifact)
const status = await DDL.readiness(adminSql, artifact)
```

`DDL.apply` rechecks the approved source hash, records the artifact once in `basis.schema_migration`, executes the ordered operations transactionally, verifies the resulting physical state, and rejects duplicate or drifted application. It returns the applied version and target hash. Invalid or interrupted application rolls back before the ledger entry is written.

`DDL.readiness` compares the live catalog with the artifact's expected physical state and never mutates the database. It reports concrete discrepancies and is meant for readiness checks, not automatic startup migration. Operations containing `CONCURRENTLY` use the explicit nontransactional path under a session advisory lock; failures are recorded as failed ledger entries and never presented as readiness.
