# Leaf-Authorized CTE Authorization Design

Status: design gate only. No query compiler, Graph authorization, RLS, MTG, or migration change is included in this document.

## Current role and SQL evidence

The managed database currently has a restricted application login role `basis_app`, a database owner role, and no separate trusted query executor. The test fixture reports:

```text
current_user = basis_app
session_user = basis
current_schema = fixture schema
Entity SELECT privilege = true
Entity RLS = enabled
Entity force RLS = true
Entity owner = basis
basis_app superuser = false
basis_app BYPASSRLS = false
```

`ManagedPostgresService.provisionApplicationRole` creates `basis_app` with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`. `Database.sql` exposes the same connection's raw Bun SQL client. `Database.tx` exposes raw SQL inside a transaction. `Database.query` also uses that connection and sets `actor.id` through `set_config`. An arbitrary caller with raw SQL can change `actor.id` itself.

The current leaf-only policy proposal therefore cannot be made safe by changing RLS alone. The execution role and SQL entry surface must change.

## Proposed privilege model

The recommended model is:

- `basis_owner` or the existing database owner: NOLOGIN schema owner, migrations and trusted operational DDL only.
- `basis_executor`: LOGIN role used only by trusted Basis query/mutation machinery. It has ancestor read privileges, no `SUPERUSER`, no `BYPASSRLS`, and is not the table owner. Leaf RLS still applies to it.
- `basis_app`: LOGIN role used by untrusted application SQL. It has no domain-table access and cannot establish a trusted actor context. It is never granted membership in `basis_executor`.

The important boundary is not whether a statement is written by Basis. It is whether the role submitting the statement can submit arbitrary SQL and whether it can establish actor identity.

### Illustrative DDL

```sql
CREATE ROLE basis_executor LOGIN PASSWORD :'executor_password'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;

CREATE ROLE basis_app LOGIN PASSWORD :'app_password'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;

GRANT CONNECT ON DATABASE basis TO basis_executor, basis_app;
GRANT USAGE ON SCHEMA public, basis TO basis_executor;

GRANT SELECT, INSERT, UPDATE, DELETE
  ON ALL TABLES IN SCHEMA public
  TO basis_executor;

-- Untrusted raw SQL has no domain access.
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM basis_app;
REVOKE ALL ON ALL TABLES IN SCHEMA basis FROM basis_app;
GRANT USAGE ON SCHEMA basis TO basis_app;

-- Ancestor storage is not an authorization boundary for the trusted executor.
ALTER TABLE "Entity" DISABLE ROW LEVEL SECURITY;
-- Concrete leaf RLS remains enabled and forced.
```

The final grants must be generated from the canonical Graph and reviewed as a release artifact. They are not proposed as hand-maintained production SQL.

## Execution flow

1. The HTTP request resolves one actor identity through the trusted Basis request context.
2. `Database.query` compiles the query against the canonical Graph and uses the `basis_executor` pool.
3. It starts a transaction and sets the actor context; the actor value comes only from the trusted request context, never from request SQL.
4. The compiler emits leaf-rooted authorized CTEs over `basis_executor`; concrete leaf RLS applies inside the CTE.
5. Untrusted route code has no `basis_executor` credential and no raw domain SQL client.
6. If an application must execute raw SQL, it uses `basis_app`; that role can read no domain table and therefore cannot read ancestor storage or spoof an actor into a readable leaf.

`Database.sql` and raw `Database.tx` cannot remain on the untrusted route context under the recommended model. Trusted Graph mutations and compiled queries remain on the `basis_executor` boundary.

## CTE shape

```sql
WITH authorized_printings AS NOT MATERIALIZED (
  SELECT
    leaf.id,
    printing."card.id",
    root.name
  FROM "CustomPrinting" leaf
  INNER JOIN "Printing" printing ON printing.id = leaf.id
  INNER JOIN "Entity" root ON root.id = leaf.id
)
SELECT ...
FROM authorized_printings p;
```

The leaf table is the authorization boundary. `Printing` and `Entity` are inherited storage only. Abstract targets compose one authorized CTE per concrete leaf with `UNION ALL` and expose the runtime discriminator.

## Executable privilege tests required before implementation

```sql
-- 1. Untrusted role cannot read ancestors.
SET ROLE basis_app;
SELECT id, name FROM "Entity"; -- must fail: permission denied

-- 2. Untrusted role cannot establish a trusted actor and read a leaf.
SET ROLE basis_app;
SELECT set_config('actor.id', '<another-user>', false);
SELECT * FROM "CustomPrinting"; -- must fail: no table privilege

-- 3. Trusted executor can run a leaf CTE under leaf RLS.
SET ROLE basis_executor;
WITH authorized AS (
  SELECT leaf.id, root.name
  FROM "CustomPrinting" leaf
  INNER JOIN "Entity" root ON root.id = leaf.id
)
SELECT * FROM authorized; -- authorized leaves only

-- 4. Leaf RLS is still active for the trusted executor.
SELECT has_table_privilege('basis_executor', '"CustomPrinting"', 'SELECT');
SELECT relrowsecurity, relforcerowsecurity FROM pg_class WHERE oid = '"CustomPrinting"'::regclass;

-- 5. Trusted executor is not owner, superuser, or BYPASSRLS.
SELECT r.rolsuper, r.rolbypassrls, pg_get_userbyid(c.relowner)
FROM pg_roles r
JOIN pg_class c ON c.oid = '"CustomPrinting"'::regclass
WHERE r.rolname = 'basis_executor';
```

## Decision required before implementation

The operator must settle whether arbitrary raw application SQL remains available.

- **Recommended: no raw domain SQL from untrusted application code.** `Database.query` and Graph-native mutations use `basis_executor`; `basis_app` has no domain-table access. This is the smallest safe boundary.
- **If arbitrary raw SQL must remain**, it needs a separate privilege boundary with no readable domain tables. A raw role that can read leaves AND set `actor.id` can spoof the actor. A security-definer function is excluded by the architecture; ancestor RLS and denormalization are rejected alternatives.

No implementation may start until this decision and the generated grant review are approved.
