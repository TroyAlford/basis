# Query Language

`db.query` has one semantic contract and two input spellings: structured JSON filters and source string expressions. Both normalize to the same canonical filter tree and compile through the same `SQL.where` path. This page is the contract for the query language: what is implemented now, the accepted end-state grammar for the remaining query stages, and the boundaries that are deliberately excluded.

## Pipeline and ownership

The components have distinct jobs:

- `QueryLexer` tokenizes source text and records source spans.
- `QueryParser` builds a transient, non-executable syntax tree and reports syntax diagnostics.
- `QueryNormalizer` applies entity metadata to parsed syntax and lowers string forms to canonical filters.
- `Predicate` validates structured filters and performs shared logical/operator expansion.
- `compilePolymorphicQuery` owns field resolution, projection joins, collection envelopes, finite work budgets, and the one SQL statement that is executed through Bun SQL.

No input form gets its own executor or database path. A query is either compiled completely or rejected before execution.

## Field universe

`where` and `orderBy` resolve against the effective fields of the queried entity:

- Root scalars: `id`, `name`, `String`, `Number`, `Boolean`, `Date`, `Timestamp`.
- Inherited scalars, including fields owned by an MTI ancestor.
- Descendant-only scalars on abstract queries when their declarations are compatible across the concrete leaves.
- Stored `Entity` references and their `Inverse` navigations are navigation metadata, not scalar columns. They are never accepted as predicates or sort fields merely because they appear in `fields`.
- `Array` and `JSON` fields remain value fields with the type-specific operators defined below. `collection.$count` is a read-only intrinsic count pseudo-field, never an authored ontology field.
- A dotted path may appear only where the current stage explicitly accepts reference or collection traversal.
- There is no separate identity field such as `ownerId`; identity is the reference's canonical target `id`.
- Unknown, incompatible, navigation-only, and physical storage names are rejected before SQL execution.

Current predicates resolve root/effective/descendant scalar fields, model-validated singular reference paths, collection comparisons over inverse and named N:M navigations, and native Array/opaque JSON operations.

## Input forms

Structured shorthand is a single equality:

```ts
where: { title: 'Hello' }
```

An explicit structured comparison uses a closed operator vocabulary:

```ts
where: {
  operator: '$and',
  filters: [
    { field: 'score', operator: '$gte', value: 5 },
    { field: 'score', operator: '$lt', value: 10 },
    { field: 'title', operator: '$ne', value: 'Draft' },
  ],
}
```

The source form expresses the same predicate tree with `$` operators or their symbolic aliases:

```ts
where: "score >= 5 $and score < 10 $and title != 'Draft'"
```

`$and` and `$or` require a non-empty `filters` array. `$not` is unary and requires exactly one child. String source supports `!` and `$not` as compositional negation, grouping parentheses, and the symbolic aliases `=`, `>`, `>=`, `<`, `<=`, `!=`, `<>`, and `~=` (the exact alias of `$contains`). Empty or whitespace-only source is equivalent to an empty structured object: it adds no predicate.

Source errors retain lexer/parser offsets. Current normalizer errors throw the first diagnostic with its source offset; the accepted end-state remains fail-closed for every diagnostic and never executes a partially normalized query.

## Implemented scalar operators

The following code block is the current executable contract. Each entry pairs the structured and string spelling of the same canonical filter.

```ts
const scalarOperators = [
  {
    meaning: 'equality',
    structured: { field: 'title', operator: '$eq', value: 'Hello' },
    source: "title = 'Hello'",
  },
  {
    meaning: 'inequality',
    structured: { field: 'title', operator: '$ne', value: 'Hello' },
    source: "title != 'Hello'",
  },
  {
    meaning: 'less than',
    structured: { field: 'score', operator: '$lt', value: 10 },
    source: 'score < 10',
  },
  {
    meaning: 'less than or equal',
    structured: { field: 'score', operator: '$lte', value: 10 },
    source: 'score <= 10',
  },
  {
    meaning: 'greater than',
    structured: { field: 'score', operator: '$gt', value: 5 },
    source: 'score > 5',
  },
  {
    meaning: 'greater than or equal',
    structured: { field: 'score', operator: '$gte', value: 5 },
    source: 'score >= 5',
  },
  {
    meaning: 'inclusive range',
    structured: { field: 'score', operator: '$between', values: [5, 10] },
    source: 'score $between [5, 10]',
  },
  {
    meaning: 'substring',
    structured: { field: 'title', operator: '$contains', value: 'Ada' },
    source: "title $contains 'Ada'",
  },
  {
    meaning: 'empty string or NULL',
    structured: { field: 'title', operator: '$empty' },
    source: 'title $empty',
  },
  {
    meaning: 'logical AND',
    structured: { operator: '$and', filters: [/* filters */] },
    source: 'a $and b',
  },
  {
    meaning: 'logical OR',
    structured: { operator: '$or', filters: [/* filters */] },
    source: 'a $or b',
  },
  {
    meaning: 'logical NOT',
    structured: { operator: '$not', filters: [/* one filter */] },
    source: '!filter or $not filter',
  },
]
```

`$between` has exactly two bounds. A `null` bound is open; `[null, null]` is invalid. String `$empty` means exactly SQL `NULL` or the empty string, never whitespace; relationship `$empty` means zero related rows and is documented in stage 18. `$contains` is case-insensitive substring matching for `String`; wildcard characters are escaped before binding. Ranges are limited to `String`, `Number`, `Date`, `Timestamp`, and `ID`; booleans use equality only.

`$ne` lowers to `Not(Equal)`. `$between` lowers to the applicable `And` of inclusive bounds. `$empty` lowers to `Or(Equal(null), Equal(''))`. The canonical filter tree therefore has only primitive comparisons and logical groups; source-only conveniences never reach SQL as special cases.

### Null and missing semantics

Scalar predicates are two-valued, including SQL `NULL`:

- Equality to a non-null value is false for `NULL`.
- `$eq null` matches only SQL `NULL`; `$ne null` matches only non-null values.
- Range and `$contains` comparisons are false for `NULL`.
- `Not` complements the two-valued result, so `$ne 5` also matches `NULL`.
- String `$empty` matches only `NULL` or `''`; `$not $empty` matches non-null non-empty strings, including whitespace-only strings.

These rules are shared by the structured and string forms.

## Stage 17 — reference paths (implemented)

Reference predicates are now supported through the shared `db.query` path. Structured and string forms normalize through the same field-aware resolver and SQL compiler:

```ts
const referencePaths = [
  {
    meaning: 'scalar equality',
    structured: { field: 'owner.name', operator: '$eq', value: 'Ada' },
    source: "owner.name = 'Ada'",
  },
  {
    meaning: 'scalar inequality',
    structured: { field: 'owner.name', operator: '$ne', value: 'Ada' },
    source: "owner.name != 'Ada'",
  },
  {
    meaning: 'scalar ordered comparison',
    structured: { field: 'owner.score', operator: '$gte', value: 5 },
    source: 'owner.score >= 5',
  },
  {
    meaning: 'scalar range',
    structured: { field: 'owner.score', operator: '$between', values: [5, 10] },
    source: 'owner.score $between [5, 10]',
  },
  {
    meaning: 'scalar substring',
    structured: { field: 'owner.name', operator: '$contains', value: 'Ada' },
    source: "owner.name $contains 'Ada'",
  },
  {
    meaning: 'scalar empty',
    structured: { field: 'owner.name', operator: '$empty' },
    source: 'owner.name $empty',
  },
  {
    meaning: 'identity equality',
    structured: {
      field: 'owner',
      operator: '$eq',
      value: '00000000-0000-4000-8000-000000000001',
    },
    source: "owner = '00000000-0000-4000-8000-000000000001'",
  },
  {
    meaning: 'missing reference',
    structured: { field: 'owner', operator: '$eq', value: null },
    source: 'owner = null',
  },
]
```

- A dotted path such as `owner.name` traverses stored singular `Entity` references and ends in a scalar or reference identity.
- All scalar operators above apply to a scalar-ending path; reference identity accepts equality/inequality and `null`, not ordering, substring, range, or `$empty`.
- The path must be unambiguous across abstract/descendant targets. A field with incompatible target declarations is rejected rather than guessed per row.
- A missing or null reference behaves as `NULL` for the terminal scalar. Non-null comparisons are false; `$eq null` matches absent/null, and `$ne null` matches present non-null values.
- For a scalar-ending reference path, `$empty` remains String-only and treats a null/missing reference as empty; collection `$empty` is defined separately in stage 18.
- The path uses the existing single-statement reference joins and finite work budget, including the same eight-reference-hop limit as projection. Runtime row identity is never inspected to detect cycles.
- Sorting by a dotted reference path remains excluded in stages 16–20; `orderBy` continues to accept only root/effective scalar fields.

## Stage 18 — collection comparisons (implemented)

Relationship collections use the same model-aware matching idiom that native arrays will use in stage 19. The operator states the intent; the canonical field type selects the physical implementation. `$contains` has the symbolic alias `~=`.

```ts
const collectionComparisons = [
  {
    meaning: 'at least one related item matches',
    structured: {
      field: 'pets',
      operator: '$contains',
      filters: [{ field: 'name', operator: '$eq', value: 'Ada' }],
    },
    source: "pets $contains (name = 'Ada')",
  },
  {
    meaning: 'no related item matches',
    structured: {
      filters: [{
        field: 'pets',
        operator: '$contains',
        filters: [{ field: 'name', operator: '$eq', value: 'Ada' }],
      }],
      operator: '$not',
    },
    source: "pets !$contains (name = 'Ada')",
  },
  {
    meaning: 'every related item matches',
    structured: {
      field: 'pets',
      operator: '$all',
      filters: [{ field: 'name', operator: '$eq', value: 'Ada' }],
    },
    source: "pets $all (name = 'Ada')",
  },
  {
    meaning: 'each independent requirement has a match',
    structured: {
      field: 'pets',
      operator: '$contains',
      filters: [
        { field: 'name', operator: '$eq', value: 'Ada' },
        { field: 'name', operator: '$eq', value: 'Grace' },
      ],
    },
    source: "pets $contains [(name = 'Ada'), (name = 'Grace')]",
  },
  {
    meaning: 'one related item satisfies both requirements',
    structured: {
      field: 'pets',
      operator: '$contains',
      filters: [{
        operator: '$and',
        filters: [
          { field: 'name', operator: '$eq', value: 'Ada' },
          { field: 'name', operator: '$eq', value: 'Grace' },
        ],
      }],
    },
    source: "pets $contains (name = 'Ada' $and name = 'Grace')",
  },
  {
    meaning: 'named relationship property',
    structured: {
      field: 'members',
      operator: '$contains',
      filters: [{
        field: 'membership.role',
        operator: '$eq',
        value: 'GM',
      }],
    },
    source: "members $contains (membership.role = 'GM')",
  },
  {
    meaning: 'zero related items',
    structured: { field: 'pets', operator: '$empty' },
    source: 'pets $empty',
  },
]
```

- `$contains` (`~=`) is existential: at least one related item satisfies the requirement.
- `$not $contains` is the only "none" form. There is no `$none`, `$any`, `$some`, or `$notContains` operator. `pets !$contains (P)` composes the same negation.
- `$all` is universal: every related item satisfies its one member predicate, true for zero items. It normalizes to the shared counterexample form `Not(Contains(Not(P)))`; there is no separate universal execution engine.
- `$empty` tests zero related items. On a relationship navigation, `$eq null` is invalid; `pets !$empty` means at least one related item, independent of any inner predicate.
- `pets $contains [(P), (Q)]` means `Contains(P) AND Contains(Q)`. P and Q may be satisfied by different items. `pets $contains (P $and Q)` means one item satisfies both. `pets $contains (P $or Q)` means one item satisfies either. Empty bracketed requirement lists are rejected.
- A structured `filters` array contains independent requirements. A one-item `filters` array containing an `$and`, `$or`, or `$not` tree applies that whole tree to one member. `$all` accepts exactly one member predicate.
- Inner predicates are relative to the collection item and may use the item’s scalar or singular-reference paths, including terminal identity equality and `null`; reference paths retain the same eight-hop limit as projection. Named N:M relationship properties use the established lowercase prefix, such as `membership.role`. The prefix is not available on inverse collections, and Array or JSON relationship properties are rejected as predicate targets.
- Collection comparisons preserve two-valued null behavior. A null inner scalar makes a non-null comparison false; its negation is true, and a null field is a counterexample to `$all`.
- Each independent requirement compiles to its own correlated `EXISTS`; negation uses the shared logical operator with null-safe two-valued semantics. The query remains one parameterized SQL statement with the same finite work budget. Nested collection comparisons, unbounded traversal, N+1 lookups, and application-side child hydration are rejected.

## Stage 19 — native Array and opaque JSON (implemented)

Array and JSON predicates are type-directed by the canonical field type and keep JSON opaque. Arrays use `$contains`/`~=`, `$overlaps`, `$empty`, `$eq` set equality, and `$sequenceEqual` sequence equality; JSON uses opaque `$contains`. There is no separate array/JSON predicate engine. Literal array operations use the canonical comparison node `{ field, operator, value }`; scoped member predicates use the shared collection-filter representation described in stage 19a.

```ts
const arrayOperators = [
  {
    meaning: 'contains one element',
    structured: { field: 'tags', operator: '$contains', value: 'urgent' },
    source: "tags $contains 'urgent'",
  },
  {
    meaning: 'contains every listed element',
    structured: { field: 'tags', operator: '$contains', value: ['urgent', 'important'] },
    source: "tags $contains ['urgent', 'important']",
  },
  {
    meaning: 'overlaps at least one listed element',
    structured: { field: 'tags', operator: '$overlaps', value: ['urgent', 'important'] },
    source: "tags $overlaps ['urgent', 'important']",
  },
  {
    meaning: 'unordered set equality',
    structured: { field: 'tags', operator: '$eq', value: ['b', 'a'] },
    source: "tags == ['b', 'a']",
  },
  {
    meaning: 'exact sequence equality',
    structured: { field: 'tags', operator: '$sequenceEqual', value: ['b', 'a'] },
    source: "tags === ['b', 'a']",
  },
  {
    meaning: 'empty array or NULL',
    structured: { field: 'tags', operator: '$empty' },
    source: 'tags $empty',
  },
]

const jsonOperators = [
  {
    meaning: 'object containment',
    structured: { field: 'payload', operator: '$contains', value: { kind: 'note' } },
    source: 'payload $contains {kind: "note"}',
  },
  {
    meaning: 'nested object containment',
    structured: { field: 'payload', operator: '$contains', value: { meta: { active: true } } },
    source: 'payload $contains {meta: {active: true}}',
  },
  {
    meaning: 'array containment',
    structured: { field: 'payload', operator: '$contains', value: ['a', 'b'] },
    source: "payload $contains ['a', 'b']",
  },
]
```

Array semantics are type-directed:

- `$contains` on `Array<T>` means PostgreSQL array containment `@>`. A scalar operand is normalized to a one-element array; an array operand requires every element to be contained.
- `$overlaps` means PostgreSQL array overlap `&&`; a scalar operand is normalized to a one-element requirement.
- A scalar operand is valid for both array membership operators. The operand type must match the canonical array element type, including ID format and numeric finiteness.
- `$contains []` is true for every non-null array (the empty set is contained); `$overlaps []` is false. Array columns remain non-null; empty arrays are values, not missing values. Array operand elements cannot be null.
- Null operands are invalid for array membership. Stored null array elements do not match a non-null operand and cannot be targeted by this contract’s array predicates.
- String `$contains` remains case-insensitive substring matching. JSON `$contains` means structural containment `jsonb @>`. The operator vocabulary is deliberately type-directed, not a second operator registry or a second executor.
- `tags == [...]` and `$eq` mean unordered set equality ignoring order and multiplicity; `tags === [...]` and `$sequenceEqual` mean exact sequence equality. Set equality uses PostgreSQL native `@>`/`<@` equivalence rather than per-row sorting. `===` is invalid for inherently unordered relationship collections. These are Basis DSL semantics, not JavaScript reference equality or ordinary PostgreSQL array equality.
- Array operands are capped at **128 elements** so one predicate cannot expand into an unbounded SQL statement or exhaust the driver parameter budget.
- `tags $empty` tests SQL null or zero elements; `tags !$empty` is its negation. Native-array `$all` and existential member predicates use the approved `@` syntax in stage 19a.

JSON source literals are first-class:

- The lexer/parser produces literal AST nodes for objects, arrays, strings, numbers, booleans, and null without evaluating JavaScript.
- Object keys may be quoted or bare identifiers. Nested objects and arrays are allowed. Computed keys, spreads, functions, and arbitrary expressions are rejected.
- `payload $contains {kind: "note"}` and `payload $contains {meta: {active: true}}` parse without requiring a serialized JSON string. A JSON string operand uses an ordinary quoted literal; JSON null uses `null`; object keys may be quoted or bare. Source numeric literals that fall outside JavaScript's safe integer range, or whose exact decimal value cannot survive Number plus JSON serialization, are rejected instead of being silently rounded; PostgreSQL `jsonb` retains exact numeric values.
- Structured and source operands normalize to the same comparison node and the same field-type-aware predicate. JSON null and an absent key are distinct; `$contains` performs structural containment without path traversal, schema validation, or treating JSON as an entity graph. JSON `$eq`/`===` equality and JSON path predicates are not part of this contract.
- JSON fields remain non-null columns. Empty objects and empty arrays are values, not missing values; no JSON empty operator is introduced.

## Stage 19a — scoped member predicates (implemented)

`@` names the innermost current collection member. It is never inferred as an implicit left operand or resolved against an outer entity. Literal membership such as `tags $contains 'urgent'` and `tags $contains ['urgent', 'important']` remains unchanged. Bracketed member requirements are independent, so `scores $contains [(@ = 1), (@ = 2)]` requires both values across the array, while `scores $contains (@ = 1 $and @ = 2)` requires one element to be both.

```ts
const scopedMemberPredicates = [
  {
    meaning: 'native array existential member predicate',
    structured: {
      field: 'scores',
      operator: '$contains',
      filters: [{ field: '@', operator: '$gte', value: 10 }],
    },
    source: 'scores $contains (@ >= 10)',
  },
  {
    meaning: 'native array universal member predicate',
    structured: {
      field: 'scores',
      operator: '$all',
      filters: [{ field: '@', operator: '$gt', value: 0 }],
    },
    source: 'scores $all (@ > 0)',
  },
  {
    meaning: 'single member satisfying multiple conditions',
    structured: {
      field: 'scores',
      operator: '$contains',
      filters: [{
        operator: '$and',
        filters: [
          { field: '@', operator: '$gt', value: 5 },
          { field: '@', operator: '$lt', value: 20 },
        ],
      }],
    },
    source: 'scores $contains (@ > 5 $and @ < 20)',
  },
  {
    meaning: 'entity collection member path',
    structured: {
      field: 'pets',
      operator: '$contains',
      filters: [{ field: 'age', operator: '$gt', value: 10 }],
    },
    source: 'pets $contains (@.age > 10)',
  },
  {
    meaning: 'entity collection universal member predicate',
    structured: {
      field: 'pets',
      operator: '$all',
      filters: [{ field: 'vaccinated', operator: '$eq', value: true }],
    },
    source: 'pets $all (@.vaccinated = true)',
  },
  {
    meaning: 'current entity identity',
    structured: {
      field: 'pets',
      operator: '$contains',
      filters: [{ field: 'id', operator: '$eq', value: '00000000-0000-4000-8000-000000000001' }],
    },
    source: "pets $contains (@ = '00000000-0000-4000-8000-000000000001')",
  },
]
```

- Native arrays accept `@` as a scalar member; `@.field` is invalid because array elements are scalar values. The array options are `$contains` (existential) and `$all` (universal).
- Entity collections accept `@` or `@.path`. `@` and `@.id` both mean the current member entity identity; other paths use the same typed field/reference validation as relative syntax. `pets $contains (@.age > 10)` and `pets $contains (age > 10)` normalize identically. Relationship-owned properties remain available through the established lowercase prefix, for example `@.membership.role`.
- Structured inner filters are relative to the member. Native-array members use the canonical pseudo-field `@`; entity collections use their normal relative field names, and `@`/`@.id` normalize to `id`.
- `$all` is vacuously true for an empty array or collection; `$contains` is false. Existing two-valued NULL behavior applies to member comparisons. Literal array membership, `$empty`, array set/sequence equality, and opaque JSON containment retain their stage-19 semantics.
- Arrays compile with `unnest` and entity collections with the existing correlated semijoin. Nested collection correlation, outer-context captures, JSON structural equality, and implicit `@` operands are rejected. A quantifier must contain a non-empty member predicate list.

## Stage 20 — query parity gate (implemented)

The full query language is now covered by an integration parity gate. Equivalent structured filters and string expressions must produce the same canonical filter semantics, SQL, bindings, results, and applicable errors.

The gate covers:

- root, inherited, and descendant scalar fields, including abstract-query leaves;
- singular reference paths, reference identities, nullable/missing references, and descendant reference targets;
- inverse and named N:M collections, relationship properties, literal `$empty`/`$contains`/`$all`, and explicit `@`/relative member paths;
- native Array literal membership, set/sequence equality, `@` member predicates, and opaque JSON containment;
- two-valued NULL behavior, source diagnostic offsets, finite reference depth, array operand bounds, and query work budgets;
- stable source ordering, pagination, collection-preview bindings, and real PostgreSQL result parity.

`QueryParity.test.ts` owns compiler/error/diagnostic/budget parity; `QueryParity.e2e.ts` owns the real PostgreSQL inherited/abstract, dotted-path, relationship, Array/JSON, NULL, scoped-member, and pagination matrix. Existing stage-specific contract and E2E suites remain the detailed behavior fixtures. Authorization and RLS are deliberately outside this gate; collection `$count` and relational-planning validation are covered by stage 20a, and security deployment by 20b–20e.

## Stage 20a — collection counts and relational planning (implemented)

Inverse, named-relationship, and native-array collections expose a read-only `$count` intrinsic:

```ts
const countPredicates = [
  { structured: { field: 'pets.$count', operator: '$gte', value: 3 }, source: 'pets.$count >= 3' },
  { structured: { field: 'scores.$count', operator: '$gt', value: 0 }, source: 'scores.$count > 0' },
]
```

- `$count` is valid in predicates, projections, and supported root collection/array `orderBy` paths. It is rejected on scalars and singular references.
- Relationship counts count complete logical member/edge rows, independent of collection preview limit/offset. Native-array counts include duplicates and stored null elements; a NULL array counts as zero.
- Relationship `collection.$count = 0` canonicalizes to `NOT EXISTS` and `collection.$count > 0` to `EXISTS` when equivalent; native-array counts use `cardinality`. Other count thresholds use the shared grouped count CTE selected by the measured stage-20a renderer.
- Collection relation planning is shared by predicate scopes, collection previews, counts, and count ordering. Plans are keyed by logical path and physical parent occurrence, so sibling descendant-reference variants do not share the wrong parent alias; emitted subquery work remains charged to the finite compiler budget.
- The planning benchmark fixture runs `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` over correlated and CTE default/`MATERIALIZED`/`NOT MATERIALIZED` variants on representative parent/child cardinalities, including selective and nonselective count thresholds. All variants return the same rows; the evidence selects default CTE rendering for count aggregates while correlated rendering remains in use for collection predicates/previews. No blanket `MATERIALIZED` rule is applied.
- The exported `QueryScope`, `CollectionScope`, `ArrayScope`, and `CountScope` types form the reusable entity/relationship scope boundary for later authorization work. They do not implement permission policies, RLS, or request actor binding in this stage.

Representative evidence from the analyzed 24-parent / 70-child fixture (local PostgreSQL; timings are illustrative, not CI thresholds):

## Ordering, pagination, and exclusions

`orderBy` accepts only effective root/inherited/descendant scalar fields. It rejects references, inverse/N:M collections, dotted reference paths, Array, and JSON. Abstract queries append the stable `id` tie-break and use `name, id` when no ordering is supplied. `limit` defaults to 25 and must be a non-negative integer or `null`; `offset` must be non-negative. Pagination bindings preserve the predicate/collection/work-budget ordering.

Explicit exclusions for this contract:

- No raw SQL fragments, arbitrary JSONPath, regex operators, `$blank`, `$notblank`, `$nor`, `$xor`, or a second predicate grammar.
- No predicates on physical columns, `Inverse` fields as scalar values, or implicitly inferred inverse edges.
- No collection predicates that fetch all children into application code, perform N+1 lookups, nest collection comparisons, or recursively traverse collection elements. No JSON path traversal, JSON equality, nested `@` correlation, or outer-context captures.
- No runtime row-identity cycle detection; only canonical static traversal and reciprocal-backtrack rules apply.
- No schema generation, migrations, ORM writes, or automatic CRUD routes from the query language.

## Executable contract fixtures

`libraries/server/source/QueryContract.test.ts` locks the implemented contract: structured and string forms normalize to the same canonical filter and compile to the same SQL, and unsupported forms above are rejected before execution. The fixture names are the approval boundary for subsequent query-stage changes: extending an operator or field kind requires changing the contract fixture and the implementation together.

## Current implementation audit

- `QueryLexer` and `QueryParser` own field, scoped `@` member, comparison, logical, grouping, collection-comparison, and first-class Array/JSON literal syntax and source spans.

- `QueryNormalizer` applies scalar metadata and accepts the query compiler’s field, reference-path, and collection resolvers. It lowers `$all` to the shared counterexample canonical form.
