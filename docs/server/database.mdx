# Database & Transactions

`server.database()` gives the server one owned PostgreSQL capability, exposed as `server.db`. Managed mode is zero-config: Basis keys the database to the normalized application working directory, lets Docker allocate a loopback port, reconciles an existing app-owned service, and waits for the pool before reporting healthy. The service and its data outlive any one web-server process.

Pass `url` only when using an explicit external PostgreSQL server. Managed state and credentials live inside the installation under `.basis/database/`; Basis writes a local ignore file and static serving never exposes `.basis`.

## Canonical entities

`EntityDefinitions.load(source)` parses and validates the canonical JSON entity definitions. JSON is the authority; the loader does not create tables, initialize a schema, or run migrations.

```json
{
  "entities": [
    {
      "name": "User",
      "fields": [
        {
          "field": "id",
          "format": "UUID"
        },
        {
          "field": "email",
          "type": "String"
        }
      ]
    },
    {
      "name": "SystemUser",
      "extends": "User",
      "fields": [
        {
          "field": "permissions",
          "type": "String"
        },
        {
          "field": "manager",
          "type": "Entity",
          "target": "User",
          "column": "managerId"
        }
      ]
    },
    {
      "name": "Client",
      "extends": "User",
      "fields": [
        {
          "field": "company",
          "type": "String"
        }
      ]
    }
  ]
}
```

```ts
import { EntityDefinitions, FieldType } from 'basis/server'

const entities = EntityDefinitions.load(await Bun.file('./entities.json').text())
const user = entities.entity('User')
```

Entity definitions use `name`, optional `extends`, and mandatory `fields`. Field descriptors always start with `field`; scalar fields use the exact serialized types `ID`, `String`, `Boolean`, `Date`, `Number`, and `Timestamp`, and singular references use `Entity` with explicit `target` and `column`. `fields` may be empty. There is no authored primary-key flag, alternative primary-key name, or authored `abstract` boolean.

The implicit system root owns `id: ID`, `name: String`, and the concrete-leaf `entity` discriminator. The universal lightweight object shape is `{ id, name, entity }`. `id` is always the primary key; every physical table receives generated `id text primary key` storage and a parent foreign-key column. `name` replaces the former display-name column everywhere. Root field names are reserved from ordinary declarations.

Identity and ordinary fields are inherited. The only inherited refinement is an `id` entry containing `format` and no `type`:

- `format: UUID` narrows the shared identity to canonical lowercase UUID text.
- `format: Snowflake` narrows it to canonical signed-64-bit decimal text.
- Without a refinement, ID accepts either format.
- A descendant inherits an ancestor format; a conflicting redeclaration is rejected.

The required fixture above derives `User` as abstract because it has children, and derives `SystemUser` and `Client` as concrete leaves. A standalone entity with `fields: []` is a valid concrete entity. A branch cannot be instantiated; only leaf names may appear as root discriminators.

The model is logical-first. A singular entity reference is itself a field in `fields`: `SystemUser.manager` is the logical field, while `managerId` is only its explicit PostgreSQL storage column. A reference uses `type: "Entity"`, an explicit `target`, and an explicit `column`. There is no inference from names, suffixes, columns, or entity existence. Reference names and physical column names are independently authored. The target must exist; the generated reference column is `text` and targets the target table's shared `id`.

Entity-rooted `db.query` uses the logical local-field vocabulary. A reference field such as `manager` is not selectable, filterable, or sortable until singular graph projection is implemented, and its physical `managerId` column is not a logical field. Direct `db.sql` remains physical SQL and may use generated columns normally.

## Universal identity root

Every initialized schema includes a system `"Entity"` table. Its `id` is exact `text`; the root format check accepts either a canonical lowercase UUID or a canonical signed 64-bit decimal string. `name` and the concrete-leaf `entity` discriminator are non-null text columns. `Entity` is reserved and cannot be declared as an application entity.

The root has a B-tree index on `(name, id)` for stable sorted/paged access and a `pg_trgm` `gin` index on `name` for indexed `ILIKE '%term%'` lookup. Initialization enables `pg_trgm` and creates both indexes. Its leaf check accepts only derived concrete entity names. Polymorphic query execution remains deferred.

## Creating physical tables

A fresh database is initialized explicitly from the same canonical definitions:

```ts
const entities = EntityDefinitions.load(await Bun.file('./entities.json').text())
await entities.createTables(server.db.sql)
```

`createTables` enables `pg_trgm`, creates the universal `"Entity"` identity root, and creates one ordinary PostgreSQL table per entity. Local scalar fields use their logical field name; a singular reference field uses its explicit `column` name. Every table gets generated `id text primary key` storage. `String` maps to `text`; `Number` to `double precision`; `Date` to `date`; `Timestamp` to `timestamptz`; `Boolean` to `boolean`. Format checks apply to the effective `id` format.

Each entity table has a real primary key and an MTI parent foreign key to the system `Entity` root or its parent table. Shared fields are stored only in the table that owns them. The root alone stores `name` and the concrete-leaf `entity` discriminator. Multi-tier chains therefore use ordinary PostgreSQL PK/FK joins, not `INHERITS`.

The statements are deterministic and available through `entities.ddl`: table and index statements run in declaration order, followed by MTI parent constraints, reference constraints, and commit-time lifecycle checks. Constraints are `deferrable initially immediate`, so normal operations validate immediately while a transaction can explicitly defer validation for mutually dependent inserts:

```ts
await server.db.tx(async sql => {
  await sql`set constraints all deferred`
  await sql`
    insert into "Entity" ("id", "name", "entity")
    values (${userId}, 'User', 'User'), (${carId}, 'Car', 'Car')
  `
  await sql`insert into "User" ("id", "carId") values (${userId}, ${carId})`
  await sql`insert into "Car" ("id", "userId") values (${carId}, ${userId})`
})
```

Commit-time constraint triggers reject an incomplete root/leaf chain, a leaf discriminator that does not match, or an incompatible second leaf. The leaf discriminator and leaf identity are immutable after creation. Temporary create/delete and sibling-leaf events are evaluated against surviving final state.

`createTables` is a fresh-schema compiler, not a migration planner. Existing tables and columns are not migrated. Existing lifecycle functions and triggers are inspected through the PostgreSQL catalog: matching definitions are left untouched, missing definitions are created, and mismatching definitions fail visibly. Initialization runs through the existing Bun transaction; it never drops and recreates matching integrity triggers during a rerun. Changing deployed columns, indexes, constraints, or ancestry requires a reviewed migration artifact and is not performed automatically at application startup.

Instance writes use parameterized `db.sql` inside `db.tx`; Basis does not expose an ORM, repository methods, or automatic CRUD routes.

A separate reviewable `DDL.plan`/`DDL.apply` workflow is the intended next schema-evolution API. It is intentionally not implemented by this compiler: there is no plan artifact, snapshot ledger, rename heuristic, or automatic startup migration here.

## `db.query`

Attach the same canonical definitions to the database capability, then project root scalar fields from one entity. MTI leaf identity and descendant expansion remain deferred, so an abstract entity query currently exposes only that table's own scalar fields:

```ts
import { EntityDefinitions, Operator, Server, SortDirection } from 'basis/server'

const entities = EntityDefinitions.load(await Bun.file('./entities.json').text())
const server = new Server()
  .database({ entities })
  .start()

const notes = await server.db.query<{ id: string, title: string }>('Note', {
  fields: ['id', 'title'],
  where: { title: 'Hello' },
  orderBy: { field: 'createdAt', direction: SortDirection.Descending },
  limit: 20,
  offset: 0,
})
```

```ts
const filtered = await server.db.query<{ id: string, title: string }>('Note', {
  fields: ['id', 'title'],
  where: {
    operator: Operator.Logical.And,
    filters: [
      { operator: Operator.Comparison.GreaterThanOrEqual, field: 'score', value: 5 },
      { operator: Operator.Comparison.LessThan, field: 'score', value: 10 },
      { operator: Operator.Comparison.Equal, field: 'active', value: true },
    ],
  },
  orderBy: { field: 'score', direction: SortDirection.Descending },
})
```

```ts
const matching = await server.db.query<{ id: string, title: string }>('Note', {
  fields: ['id', 'title'],
  where: 'score >= 5 $and score < 10 $and title !$empty',
})
```

`fields` is required and must be a non-empty list of the named entity's root fields. `where` accepts a single-field equality shorthand (`{ title: 'Hello' }`), an explicit canonical filter tree using the exported `Operator` enums, or a string query expression. An empty or whitespace-only string expression adds no predicate, matching an empty structured object. Shorthand is only equality for one field and normalizes to `Operator.Comparison.Equal`; multiple structured fields must be expressed explicitly with `And` and `filters`. An operator-looking object inside a field value is equality with that whole object, not operator syntax.

Structured and string filters normalize to the same canonical predicate tree and SQL path. Comparisons use `$eq`, `$gt`, `$gte`, `$lt`, `$lte`, `$ne`, `$between`, and `$empty`; string expressions also accept `=`, `>`, `>=`, `<`, `<=`, `!=`, and `<>`. `$between` takes exactly two inclusive bounds and uses `values: [lower, upper]` in structured form or `[lower, upper]` after the operator in string form (`score $between [5, 10]`); a `null` bound is open, while `[null, null]` is invalid. `$empty` has no value and is valid only for string fields. `$ne` lowers to `Not(Equal)`, `$between` lowers to `And` of its bounds, and `$empty` lowers to `Or(Equal(null), Equal(''))`. Logical filters use `$and` or `$or` with a non-empty `filters` array and unary `$not` with exactly one child; string expressions support `$and`, `$or`, `$not`/`!`, and grouping parentheses. `$blank`, `$notblank`, `$nor`, and `$xor` are not part of the vocabulary.

Predicate evaluation is two-valued, including on SQL `NULL`. Equality to a non-null value and range comparisons are false on `NULL`, and `Not` complements that result. Therefore `$ne 5` matches rows whose field is `NULL` as well as rows that are not `5`; `$eq null` matches only `NULL`, and `$ne null` matches only non-`NULL`. `$empty` matches exactly `NULL` or `''`, not whitespace-only strings; not-empty is `Not(Empty(field))` and does match whitespace-only strings.

Unquoted literals are typed from the target field, and quoted values remain strings. ID operands accept canonical UUID or Snowflake text; exact bigint Snowflake inputs normalize to canonical text. Every value is passed as a SQL parameter. Range operators are limited to ordered scalar fields (`String`, `Number`, `Date`, `Timestamp`, and `ID`), not `Boolean`. ID ordering and ranges compare canonical text. Unknown fields, operators, malformed nodes, incompatible literal types, or incompatible field/operator combinations fail before SQL runs.

UUID and Snowflake values remain canonical text in `db.query` results; there is no implicit bigint conversion for identity values. Ordering and comparisons operate on the physical text identity.

`orderBy` is optional and accepts a field name, an `{ field, direction }` object, or an array of those for multi-level ordering; direction uses `SortDirection` and defaults to ascending. `limit` defaults to 25 and `offset` defaults to 0; both are non-negative integers. Pass `limit: null` explicitly for unlimited rows — `undefined` keeps the default 25. Without `orderBy`, row order is unspecified, so use explicit ordering when paging deterministically. Invalid limits/offsets fail before SQL runs; validated identifiers are quoted. Identity values are returned as canonical text from `db.query`; raw `db.sql` keeps Bun's native PostgreSQL decoding for non-identity SQL. This step intentionally supports scalar root projections only — relationships and graph projections arrive in later steps.

## `db.sql`

`server.db.sql` is the pooled Bun SQL tagged-template API. Interpolations are parameters and results and errors are Bun's own.

```ts
const owner = 'Troy'
const notes = await server.db.sql<{ id: string, title: string }[]>`
  select id, title from notes where owner = ${owner}
`
```

## `db.tx`

`server.db.tx(callback)` establishes one transaction boundary. The callback receives Bun's native transaction-scoped SQL client, conventionally named `sql`. Everything run through that client is one atomic operation:

```ts
const noteId = await server.db.tx(async sql => {
  const [note] = await sql`insert into notes (title) values (${title}) returning id`
  await sql`insert into audit (action, note_id) values ('created', ${note.id})`
  return note.id
})
```

Bun commits when the callback completes successfully, and `db.tx()` resolves with the callback's return value after commit. Returning early commits. Throw to abort:

```ts
try {
  await server.db.tx(async sql => {
    await sql`insert into notes (title) values (${title})`
    throw new Error('do not keep this note')
  })
} catch {
  // The transaction rolled back.
}
```

A thrown error or failed query that escapes the callback rolls back and rejects. Await every query inside the callback; the transaction-scoped client must not be used after it completes. Queries through `server.db.sql` do not automatically join the transaction; use the callback's `sql`.

### Savepoints

`sql.savepoint(callback)` provides partial rollback inside the outer transaction. Catching the savepoint failure leaves the outer transaction usable:

```ts
await server.db.tx(async sql => {
  await sql`insert into notes (title) values (${title})`
  try {
    await sql.savepoint(async savepoint => {
      await savepoint`insert into audit (action) values ('discarded')`
      throw new Error('discard only this savepoint')
    })
  } catch {
    // Only the savepoint rolled back.
  }
  await sql`insert into audit (action) values ('committed')`
})
```

### Query cancellation

`query.cancel()` cancels one executing query. A cancellation that reaches the PostgreSQL server aborts the current transaction; catching the error alone does not make that transaction usable. Recover with a rollback or a savepoint, or let the error escape `db.tx()` so the transaction rolls back.

```ts
await server.db.tx(async sql => {
  try {
    await sql.savepoint(async savepoint => {
      const query = savepoint`select pg_sleep(30)`.execute()
      setTimeout(() => query.cancel(), 100)
      await query
    })
  } catch {
    // The savepoint rolled back; the outer transaction continues.
  }
  await sql`insert into audit (action) values ('continued')`
})
```

## Lifecycle and ownership

The server owns each process's pool and closes it on shutdown. In managed mode Docker owns the container and durable data volume; stopping or redeploying the web server does not stop PostgreSQL. Different installation directories are isolated, and a second process for the same installation attaches to the same service.

Docker is required for managed mode. An unavailable Docker daemon or failed connection makes startup report `503 error` on `/api/health`.
