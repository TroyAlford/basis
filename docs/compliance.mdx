# Compliance

`basis compliance` is Basis's authoritative paradigm gate. It runs the same style policy and typecheck as `basis lint`, then adds every Basis architecture and infrastructure opinion. It bans alternatives rather than reporting a preference.

```bash
bunx basis compliance
```

`basis lint` is the lightweight entry point: formatting, style, and typecheck only. `basis format` applies the style autofixes. There is no separate `basis check`; run `basis compliance` for the full gate or `basis lint` for the fast one, not both.

## One policy, one engine

Compliance extends the existing compliance surface. It does not introduce another command tree, configuration hierarchy, or lint engine. `basis/eslint` remains the style policy; the compliance configuration adds the paradigm rules and always uses the Basis-owned configuration, even when a consumer carries its own ESLint config.

Compliance covers:

| Rule                                          | Prohibits                                                                                                                                                                                                                         | Canonical replacement                                                                           |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `@basis/component-architecture`               | React function components, hooks, `React.FC` types, and direct `React.Component` subclasses in application source                                                                                                                 | Classes extending the Basis `Component` or `Editor` hierarchy                                   |
| `@basis/no-direct-process-spawn`              | `Bun.spawn`, `Bun.spawnSync`, Node `child_process` spawn/exec variants, and common wrappers that duplicate one-shot process execution                                                                                             | `run`, `runAsync` from `basis/utilities`                                                        |
| `@basis/no-custom-test-server`                | Direct `Bun.serve`, `http.createServer`, manual server subprocess setup, Basis `Server` construction in application test lanes, and managed database provisioners (`createDatabase`, `ManagedDatabase`, `ManagedPostgresService`) | `useApplication` for application journeys; `withDatabase` for database and authorization proofs |
| `@basis/no-direct-application-navigation`     | `page.goto`, `page.reload`, `page.goBack`, and `page.goForward` in browser-backed tests                                                                                                                                           | `useApplication(...).visit(path, fn)`                                                           |
| `@basis/no-custom-database-fixture`           | Consumer-owned PostgreSQL containers, test DB provisioning, and homemade database fixtures                                                                                                                                        | `withDatabase`                                                                                  |
| `@basis/no-committed-test-database-write`     | Durable/committed-write helpers such as `withDurableDatabase` and `withCommittedDatabase` in tests                                                                                                                                | `withDatabase`; every test transaction auto-rolls back                                          |
| `@basis/no-test-database-isolation-framework` | Custom schemas, independent test databases, and alternative per-test database managers                                                                                                                                            | `withDatabase` and the single run-scoped Basis fixture                                          |
| `@basis/no-direct-browser-lifecycle`          | `chromium.launch`, `firefox.launch`, `chromium.connect`, Playwright run-server, and manual browser/context ownership                                                                                                              | Basis-managed browser via `useApplication().visit()`                                            |
| `@basis/no-alternative-test-renderer`         | `@testing-library/react`, `react-test-renderer`, Enzyme, and equivalent custom mounted-render utilities                                                                                                                           | `render`, `Simulate`, `waitFor` from `basis/testing`                                            |
| `@basis/no-alternative-screenshots`           | `page.screenshot()`, `locator.screenshot()`, custom PNG/baseline comparators, and Playwright screenshot assertions                                                                                                                | `matchScreenshot`                                                                               |
| `@basis/no-custom-test-lifecycle`             | Manual start/stop orchestration for shared app, browser, and DB fixtures                                                                                                                                                          | `basis/testing/bun`                                                                             |
| `@basis/no-custom-test-temp-root`             | Manual run-wide temporary-directory setup/cleanup                                                                                                                                                                                 | Basis-managed temporary root and `tempDirectory`                                                |
| `@basis/no-direct-testing-internals`          | Imports of Basis's private testing implementation files                                                                                                                                                                           | Public `basis/testing` and `basis/testing/bun` exports                                          |

## Resolution, not text matching

The infrastructure rules resolve imports and simple aliases. Named imports, aliased named imports, namespace imports, destructuring (including `require` and `await import`), and statically known member expressions are all covered. A local helper named `spawn` is not flagged; a `spawn` imported from `node:child_process` is.

A bounded runner is not an application fixture. `runAsync` from `basis/utilities` is allowed by `no-direct-process-spawn`, but using it to launch an application server still triggers `no-custom-test-server`. A manual launcher written with `Bun.spawn` triggers both rules, and the application-fixture diagnostic names `useApplication`. Constructing a Basis `Server` in an application test lane triggers the same rule, and constructing a managed database names `withDatabase` instead.

## Scope

Application source receives the architecture, process, and testing-internals rules. The testing and infrastructure rules additionally apply to the repository's established test lanes: `*.test.*`, `*.spec.*`, `*.e2e.*`, `*.screenshot.*`, and the `test`, `tests`, `testing`, `__tests__`, `fixtures`, and `__fixtures__` directories. Rules are attached to source files, not restated as naming-convention exceptions. The explicit `test:recovery` proofs that own managed install, release, cutover, and recovery services are exact-file scoped exceptions under `no-custom-test-server`; they exist to exercise the managed-service boundary and cannot use the shared fixture transaction.

`@basis/component-architecture` deliberately leaves test, fixture, generated, and dependency files outside its application-source scope.

## Self-application

Basis follows its own rules. The only exemptions are the canonical implementations of the replacement mechanisms themselves and the small set of Basis tests whose subject is the test lifecycle surface. Those paths are listed explicitly in `libraries/eslint-plugin/compliance.ts`; a consumer cannot opt out by naming a file `*.lifecycle.*` or putting it in a `testing` directory.

## Escape hatches

Compliance always applies the Basis-owned configuration, so a repository config that turns a rule off does not weaken the command. For a single deliberate boundary, use an inline disable with a reason:

```ts
// eslint-disable-next-line @basis/no-direct-process-spawn -- This probes the host runtime before Basis is available.
Bun.spawnSync([process.execPath, '--version'])
```

Use the escape hatch deliberately and remove it when the boundary no longer applies. Prefer the canonical Basis mechanism whenever it can express the behavior.
